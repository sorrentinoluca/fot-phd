Introduction** Industrial process fault detection and diagnosis (FDD) is tied directly to plant safety, equipment protection, and production losses [1, 2, 3]. Classical model-based and data-driven FDD methods—including principal component analysis (PCA), support vector machines, and neural networks—perform well on benchmark datasets such as the Tennessee Eastman Process (TEP) [4, 5]. Their outputs, however, are usually fault labels, statistics, and scores rather than operator-facing explanations. LLMs offer a natural way to turn such outputs into fault summaries, recommendations, and causal narratives [16, 17]. Early LLM-assisted FDD work has already shown this direction for post-hoc explanation of classifier outputs [19]. The risk is that an LLM report may contain values that look like evidence but are not tied to the current measurement vector or any diagnostic computation. In a small tool-free sanity check, an unconstrained LLM prompted with raw sensor readings has an _Untraceable Report Rate_ (URR) of 100%: every report contains at least one required structured field that cannot be traced to tool evidence. evidence-based configurations. The ReAct framework [20] provides a general approach for interleaving LLM generation with tool calls. Tool-augmented LLM systems have been used for tasks including web search, code execution, and database querying [22, 23], but their use in industrial process monitoring requires explicit attention to evidence provenance. ReAct is not treated here as the only or most token-efficient way to enforce schema compliance; its role is an auditable orchestration mechanism for settings where evidence is gathered through sequential diagnostic tools rather than preassembled into a clean table. EviFDD-Agent is designed around evidence-constrained, tool-augmented reporting. Its main device is an _Evidence Citation Schema_ : diagnostic tools populate a structured evidence record, final reports are scored field by field with _Evidence Field Traceability_ (EFT), and the LLM is evaluated as an explanation and orchestration layer rather than as a trusted transcriber of critical evidence fields. If the agent tries to finish early, the executor redirects it to the next missing tool. The contributions are: 1. an Evidence Citation Schema for linking structured diagnostic fields to tool outputs; 2. EFT, URR, and a preliminary rule-based RAS metric for measuring field traceability, report-level traceability failure, and surface-level report completeness; 3. a deployment-oriented boundary between deterministic evidence serialization and constrained LLM narrative generation; and 4. a TEP evaluation of passive, deterministic, schema-controlled, and agent configurations, plus a small tool-free sanity check. **2. Related Work** _2.1. Data-Driven Fault Detection and Diagnosis_ Fault detection and diagnosis has a long history in chemical and process systems engineering, spanning analytical models, knowledge-based systems, 3 This preprint research paper has not been peer reviewed. Electronic copy available at: https://ssrn.com/abstract=6778889 

and data-driven monitoring [1, 2, 3, 6]. With the growth of plant historians and high-dimensional sensor measurements, multivariate statistical process control became a common framework for monitoring continuous and batch processes [7, 8]. Statistical process monitoring using PCA is a foundational approach to FDD [5]. PCA projects high-dimensional sensor data onto a lower-dimensional subspace and detects anomalies via the Hotelling _T_<sup>2</sup> statistic and the Squared Prediction Error (SPE, or _Q_ -statistic), each tested against control limits derived from the _F_ -distribution or the Jackson– Mudholkar approximation [9]. The Tennessee Eastman Process remains a widely used benchmark for evaluating such methods because it provides a plant-wide nonlinear process simulation with defined fault scenarios [4, 29]. Many recent FDD pipelines combine statistical monitoring with machinelearning classifiers. Isolation Forest [10] gives a density-free anomaly score that can catch local outliers missed by a linear PCA subspace. For multi-class fault classification, gradient-boosted trees—particularly XGBoost [11]—remain a strong tabular baseline on TEP because they handle feature interactions and nonlinear process behavior well. Explainability in FDD has been pursued through local feature-attribution methods such as LIME [15] and SHAP (SHapley Additive exPlanations) [14]. SHAP attributes each model prediction to individual input variables in a game-theoretic framework. In process diagnosis, such attributions can identify which process variables contribute most to a fault classification, supporting root-cause analysis. _2.2. LLM-Augmented Fault Diagnosis_ LLMs have been used for text generation and few-shot task adaptation [16, 17], but unsupported or inconsistent statements remain a known failure mode [18]. Work at the intersection of LLMs and process monitoring is still limited. [19] proposed FaultExplainer, which feeds the outputs of a trained fault classifier to an LLM to produce post-hoc explanations on TEP. FaultExplainer shows that such narratives can be useful, but the LLM receives pre-computed outputs passively; it does not call tools, adapt evidence gathering, or check each evidence field. EviFDD-Agent instead calls tools 4 This preprint research paper has not been peer reviewed. Electronic copy available at: https://ssrn.com/abstract=6778889 

sequentially, requires reported numeric values to match tool outputs, and counts unsupported claims at the report level through URR. _2.3. Tool-Augmented LLM Agents_ Augmented language models combine LLMs with external tools, retrieval modules, or other non-parametric resources [21]. ReAct [20] interleaves generation with tool calls in a Thought–Action–Observation loop, while Toolformer [22] and ToolLLM [23] study broader API use. In process-related applications, LLM systems have been reported for process design [24] and materials discovery [25]. Less attention has been paid to whether an FDD report can be audited field by field against the computations that produced it. _2.4. Retrieval-Augmented Generation_ RAG [26] adds retrieved documents to LLM generation, and recent surveys treat it as a standard way to supply external knowledge [27]. Here, RAG retrieves prior case descriptions from a structured TEP fault knowledge base and supplies process context for the narrative part of the report. It is only one evidence source; detection statistics, anomaly scores, classifier probabilities, and SHAP variables are supplied by separate tools. Recent C&CE work has combined LLMs, analytical toolboxes, and RAG for industrial control-loop oscillation analysis [28]. The present paper focuses instead on FDD reports whose structured fields can be checked against an evidence record. **3. Methodology** _3.1. We separate three error types: Type I (citation/transcription error), where _Ri_ = _Ei_ even though _Ei_ exists; Type II (tool prediction error), where _Ei_ = _y_<sup>_∗_</sup> because the tool is wrong relative to ground truth; and Type III (unpopulated evidence), where the report gives a value for a required field that no tool populated. ReAct Agent with Evidence Enforcement_ Algorithm 1 formalizes the diagnosis loop. The enforcement mechanism operates at the _tool-call completeness_ level (lines 8–13): if the LLM generates a `Final Answer` before all five tools have been invoked, the report is _rejected_ and the agent injects a correction message listing the missing tools, forcing continued tool execution. EFT and URR are _evaluation metrics_ computed after the final report is accepted; they are not used as runtime rejection criteria. The improvement in SHAP field fidelity arises from the _sequential context structure_ of ReAct: the LLM processes each tool output in its own turn immediately before producing the corresponding report section, which reduces paraphrasing of variable identifiers. **4. Experiments** _4.1. Dataset: Tennessee Eastman Process_ The Tennessee Eastman Process (TEP) [4] is the canonical benchmark for industrial FDD. It simulates a chemical plant with 52 process variables (41 measurements + 11 manipulated variables), 1 normal operating mode (IDV(0)), and 21 fault scenarios (IDV(1)–IDV(21)) representing step changes, random variations, slow drifts, and valve sticking. Each fault class has 500 training samples and 960 test samples. Post-injection evaluation. Samples at _t ≤_ 160 in each test fault trajectory correspond to the pre-injection period, when the process is still running normally. Including these samples in classification evaluation inflates accuracy artificially. We apply a _post-injection mask_ : only samples at time steps _t >_ 160 are used for classification and agent evaluation. This yields 800 postinjection test samples per fault class (16,800 samples total for classification, 17,760 including IDV(0)). LLM experiment sampling. Due to API cost constraints, the constrained agent experiments sample a fixed number of observations per fault class from the post-injection pool using fixed random seeds for reproducibility. EviFDD-Agent addresses the next layer of the workflow, where evidence is gathered through explicit tool calls, intermediate observations are visible, and computed evidence, attribution, retrieved process knowledge, and natural-language explanation are assembled into an operator-facing report. The practical lesson is that LLMs should not sit between critical evidence and locked structured fields. In a deployment-oriented design, deterministic tools or schema-controlled serializers should populate the auditable evidence layer; the LLM should operate on top of that layer to generate narrative explanation, recommendations, and interactive tool-use traces. RAS has a narrower role than EFT/URR. EFT/URR establish evidencetraceability behavior; Table 7 checks whether the generated text contains predefined action-oriented elements. LLM-based reports add recommendation text beyond the deterministic template, and the ReAct agent preserves exact variable citations most consistently in the 210-sample check. Expert operator scoring remains necessary for stronger claims about mechanism explanations, recommendation quality, uncertainty statements, and behavior under conflicting tool outputs. _5.3. Backend Differences in URR and Runtime_ The Flash and Pro results differ mainly in transcription behavior, not in access to evidence. Flash tends to follow the evidence-copying protocol, whereas Pro more often changes the surface form of SHAP identifiers, omits the retrieved case citation, or rounds scalar values. The dedicated 210-sample per-field rerun makes this visible: Pro has `top_variables` URR = 0.157, while Flash has 0.010. The backend difference is also large in cost terms. Flash completes the 210-sample ReAct run in 0.70 h (12.0 s/sample on average), while Pro takes 8.26 h (141.5 s/sample), an 11.8 _×_ wall-time increase (Table 6). Mean token usage is also higher for Pro (21.8k vs. 10.3k tokens/sample). Under the same evidence-copying protocol, Pro is both less traceable and substantially more expensive. Accuracy Preservation and the Role of the LLM Layer_ The agent is designed to improve auditability and explanation while preserving the diagnostic decisions of the underlying classifier. The XGBoost classifier sets the fault-identification behavior, and the LLM layer packages that decision with evidence, attribution, and retrieved process context. The paired comparisons show that the agent leaves the classifier’s decisions essentially unchanged, while EFT/URR evaluate traceability and RAS provides only a preliminary rule-based screen of action-oriented report elements. _5.5. Limitations_ The current study is scoped to single-snapshot TEP diagnosis. The LLM experiments use 210 samples per backend, which supports aggregate comparisons while leaving per-class URR estimates noisy for hard faults such as IDV(3), IDV(9), IDV(13), and IDV(15). With only 10 samples per fault class, the per-class Wilson intervals are too wide to support strong faultspecific claims; the Flash URR of 1.4% is a low observed failure rate, not proof of optimality over nearby prompt or backend variants. Plant deployment would add temporal context, alarm persistence logic, and validation on processes beyond TEP. The diagnostic backbone also limits engineering applicability. XGBoost is used as a fixed classifier to study report traceability, not as a productiongrade TEP classifier. Its full post-injection accuracy is 66.6% overall and 69.3% on fault classes only, with weak F1 scores for IDV(3), IDV(9), IDV(13), and IDV(15). When the backbone predicts the wrong fault, the LLM can still produce a traceable report, but the traced decision is wrong. Practical deployment would require a stronger diagnostic model or tighter coupling between classification confidence and report generation. The knowledge base is intentionally compact: it covers 12 TEP cases, so recommendations for uncovered or unknown faults rely on nearest-neighbor retrieval. For those classes, the RAG-related EFT field measures citation fidelity to the retriever output. Full deployment would require broader case 24 This preprint research paper has not been peer reviewed. coverage and domain review of the recommendation library. The RAS experiment is a rule-based first pass over 210 generated reports; it should not be interpreted as evidence of operator value without expert human evaluation. The competitive baselines clarify the architectural choice. Exact-table prompting and validator-regeneration achieved URR = 0 once all evidence had already been assembled into a clean schema. These approaches are attractive for fixed reports, whereas ReAct exposes the tool-use trace and supports a more interactive evidence-gathering workflow. The Pro result also shows that a larger or slower backend is not automatically preferable for evidence-copying tasks. Future work should compare these alternatives under matched prompts, latency, token budgets, and report-quality criteria. _5.6. Comparison with FaultExplainer_ FaultExplainer [19] generates natural-language explanations by feeding a pre-trained classifier’s output to an LLM in a single forward pass. EviFDDAgent differs in three respects: (1) it invokes tools sequentially rather than receiving passive inputs; (2) it verifies every structured evidence field against tool evidence; and (3) it combines detection, classification, attribution, and retrieval, whereas FaultExplainer focuses on post-hoc explanation of one classifier. **6. Conclusions** This study examined evidence-traceable LLM reporting for industrial process fault detection and diagnosis. The workflow uses an Evidence Citation Schema: tools must be called before report generation, early final answers are rejected, and the accepted report is checked against the evidence record with EFT and URR. Evidence-traceable reporting requires an explicit schema interface. A passive LLM can preserve the fault class while still losing machine-checkable SHAP identifiers. Exact-table prompting, validator-regeneration, and ReAct all largely solve this structured-field problem, but with different engineering trade-offs. The deterministic template remains the simplest option for fixedfield copying; the agent is useful when the report must combine structured 25 This preprint research paper has not been peer reviewed. The Flash–Pro comparison further shows that model selection must consider evidence fidelity and runtime together.
